# Native client integration contract

The prototype contains a Python research service and independent Java components. Pinned native caller patches and in-process ONNX adapters are in [`integrations/native`](../integrations/native/README.md). The retained five-module desktop build and synthetic ISO checks cover the earlier resident and operator/supervisor checkpoint source. The latest working patch additionally connects desktop operator authentication, EOD supervisor authentication, and face login to role-specific active evidence; that exact pinned source patch now applies cleanly and the five-module reactor compiles with Maven tests skipped. A live camera/UI run remains open. The retained Android policy-session evidence records 17 Registration Client tests and eight reference camera-SBI tests on a camera-disabled API 34 emulator. Its tests cover native inference, rejection before storage, signed fixture evidence through the actual SBI parser and onboarding API, bounded policy checks, and exact-image/one-use behavior. Parser tests use fixture-backed certificate trust, simulated action metadata and repository doubles. Complete live client UI workflows and physical attack testing remain unverified. The reference Android Camera2 SBI supplies a custom signed active result bound to the exact ISO and current transaction. Other desktop capture pathways without connected proof fail closed when active checks are required. Live-person success remains unverified. The following contract records the remaining work needed for complete integration.

## Verified components

`MosipLivenessDeviceService` is a Java 8-compatible loopback HTTP adapter with workflow validation, bearer authentication, bounded reads, and timeouts. It returns unparsed JSON. Its demo performs discovery only and does not print biometric payloads.

`NativeCaptureGate` is a portable Java component that rejects wrong sessions, repeated frame sequences, missed deadlines, failed quality, unavailable PAD, and attack verdicts. It counts distinct challenge instance identifiers and binds an accepted payload to a SHA-256 digest. The exact bytes can be consumed only once. It trusts its caller to provide real inference results and system-issued challenge instance IDs. It does not verify camera attestation or signatures, generate actions, infer faces, or match identity.

The standalone Java test exercises these properties. Compiling Java code for Java 8 does not establish a working Android APK or a successful MOSIP registration.

## Desktop implementation and remaining acceptance

The patch is pinned to MOSIP Registration Client `release-1.2.0` at `935306e2fd38bff2803697468e595026b1d18cec`. It checks resident and exception-photo candidates before deduplication/storage, operator-onboarding captures, and operator/supervisor authentication candidates before the existing matcher. The operator, EOD supervisor, and face-login previews use native frame processing and bind a one-use proof to the exact JPEG candidate and role. The face-login session service fails closed if the UI does not provide its capture gate. JPEG2000 active proof is rejected; screens without connected evidence fail closed when active checks are required.

The retained reactor build, preview, and controller checks use synthetic data and injected action geometry. Remaining acceptance work is to exercise the patched official UI with a supported physical SBI, demonstrate real prompt completion and final candidate binding, cover all capture screens and device failures, and verify that no registration packet or authenticated state is produced after rejection. These steps also need to be repeated offline on supported deployment hardware.

## Android implementation and remaining acceptance

MOSIP's Android documentation describes invoking the external SBI application for biometric capture, then returning biometric data to the Registration Client. Receiving a final capture URI does not automatically grant access to continuous face frames. Source: [official Android client features](https://docs.mosip.io/1.2.0/id-lifecycle-management/identity-issuance/android-registration-client/overview/features).

The reference camera SBI now owns a Camera2 stream and runs the PAD/action session inside the capture activity. It binds the result to the exact JPEG embedded in its ISO and adds transaction-bound evidence inside the signed SBI payload. The patched client validates the existing signature/trust/timestamp/transaction first, then performs its own PAD and consumes the evidence once before storage. Do not treat a separate webcam session as proof about a different final SBI image.

The current reference SBI uses an Android-compatible runtime, normalizes JPEG orientation, and processes bounded camera buffers on a worker. Emulator instrumentation verifies native model behavior and no-camera failure, but does not measure a physical device. Its camera activity accepts validated action count, blink/turn pool, timeout and retry settings from SBI `customOpts`; `NativePadPolicy` supplies a strict serializer and the receiver rejects partial/mistyped policy. The pinned Android Registration Client patch reads its current resident/operator policy at the outbound RCAPTURE request producer and sets `CaptureRequest.customOpts`. Evidence version 2 binds the ordered completed actions, session start, effective timeout and retry usage to the exact consumed JPEG; after existing SBI signature checks, the client validates them against its current policy. This source handoff now needs a fresh build and end-to-end request verification. Measure target-device p50/p95 latency, peak RAM, thermal behavior, and recovery after backgrounding. GPU/NPU provider availability must be measured rather than inferred from a provider list on a desktop.

## Acceptance matrix still required

For each of resident, operator, and supervisor on both Desktop and Android: demonstrate passive success where permitted, uncertain-to-active escalation, valid and wrong actions, attack during active verification, face substitution/loss, timeout, maximum retries, offline operation, device disconnect, and rejection before final client acceptance. Repeat across supported L0 and real L1 devices. Record app/model/device versions and the corresponding audit session.

Physical L1 devices, deployment credentials, institution IDs, and consented human test data are external requirements. They are not supplied by writing an adapter or passing synthetic tests.

See `NATIVE_ACTIVE_CHALLENGES.md` for the current desktop preview/capture path, model conversion parity, JPEG-only binding, and the reference Android camera-owner connection. See `CAMERA_SBI_INTEGRATION.md` for its custom signed extension and remaining production trust requirements.
